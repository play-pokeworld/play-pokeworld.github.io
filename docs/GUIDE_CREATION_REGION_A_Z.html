Créer une région et un gameplay de A à Z

Tutoriel français — PokéWorld Rework 1.14.25 · sauvegarde de production : schéma 20

Ce document est un parcours de réalisation, pas seulement une liste de fichiers. Il explique les choix, les formats, les branchements et les vérifications. L’exemple suivi est Auroria, une petite région inventée : cinq lieux, un Pokémon, une capacité, une boutique, une arène, un rival, une ligue, une histoire de quatre étapes et un nouveau Carnet de terrain avec récompense persistante.

Deux choses différentes : les données d’Auroria sont un exemple pédagogique non activé dans le jeu livré. L’installateur crée une copie neuve, nommée 1.14.26-demo, utilisant le schéma 21 uniquement pour illustrer l’ajout d’un état de gameplay. Le projet de production reste en 1.14.25 / schéma 20. N’importez pas une sauvegarde de démonstration dans le jeu de production plus ancien.

Le kit complet se trouve dans docs/examples/auroria/. Les classes reproduites ci-dessous sont les vrais fichiers de ce kit. Une carte schématique est fournie ; le sprite du nouveau Pokémon est une copie provisoire de Bulbizarre, le portrait de champion et le badge réutilisent des ressources existantes. Ce ne sont pas des illustrations originales d’Auroria. Remplacez-les pour votre région.

A — Préparer un terrain de travail sûr

  1. Décompressez le ZIP dans un dossier de travail ; sauvegardez vos exports de parties.
  2. Installez Node.js 18 ou plus. Le jeu n’a pas de dépendance npm d’exécution.
  3. Ouvrez un terminal à la racine, là où se trouve package.json.
  4. Lancez le serveur puis ouvrez son adresse. Évitez file:// : les modules ES sont souvent bloqués.
  5. Lisez Rules.md avant de créer une classe. Les identifiants et commentaires du code sont en anglais ; les textes joueurs sont localisés en français et en anglais.
node --version
npm test
npm start

Pour essayer directement le kit, utilisez un nouveau dossier de destination. La commande refuse un dossier existant et n’écrit pas dans le projet d’origine :

node docs/examples/auroria/install-example.mjs
node .arena/auroria-demo/docs/examples/auroria/verify.mjs
npm --prefix .arena/auroria-demo test

Puis, dans un autre terminal :

cd .arena/auroria-demo
npm start

Arrêtez le premier serveur pour réutiliser son port, ou suivez le port libre annoncé par le second (le serveur essaie 3000 puis les ports suivants). Pour recommencer l’installation, choisissez un autre dossier vide plutôt que de réappliquer les patches dans une copie déjà modifiée. Le kit est fixé à la version 1.14.25 ; son installateur s’arrête si un point de branchement attendu a changé.

Ce que le kit ne fait pas : ajouter 150 espèces dessinées, équilibrer une campagne entière, remplacer le tutoriel initial de Kanto ou simuler une progression naturelle jusqu’à Hoenn. Son test prépare explicitement les faits de la région précédente avant de vérifier l’entrée dans Auroria.

B — Comprendre qui possède quoi

Le trajet normal d’une action est :

Panneau → commande d’un System → modèles de SaveData → SaveSystem → événement → setters UI

  • src/data/raw/ contient les transcriptions générées de l’original. Ne les modifiez pas à la main.
  • src/data/content/ contient les ajouts et remplacements écrits à la main.
  • Les dépôts PokemonDB, MoveDB, LocationDB, QuestDB, TrainerDB… joignent les tables et exposent des définitions en lecture seule. Le dépôt des espèces s’appelle PokemonDB, pas SpeciesDB.
  • src/data/save/ contient les faits propres à chaque partie : progression, objets, UID, horloges.
  • src/systems/ applique les règles, sans document, window, boutons ou chaînes HTML.
  • src/panels/ compose les widgets de src/ui/. Les panneaux ne paient pas et ne changent pas directement la collection, les statistiques ou les quêtes.
  • src/config/ déclare les règles, identifiants et limites partagés.

Ajouter n’est pas fusionner profondément

withContent(generated, content) fait l’équivalent de {...generated, ...content}. Si vous redéfinissez pikachu, toute son entrée remplace l’ancienne. Écrire uniquement {stats: [...]} supprime ses champs requis. Copiez l’entrée complète et ne changez que les champs souhaités.

Pour les listes, withContentList remplace une entrée de même clé à sa place et ajoute les nouvelles à la fin. Les quêtes sont identifiées par catégorie + id. L’ordre des quêtes principales est l’ordre de la table, pas le tri numérique de leur id.

N’écrivez jamais dans _entries d’un dépôt pour ajouter du contenu : modifiez les tables puis rechargez complètement la page. Les dépôts et les pools de capacités sont construits et mis en cache.

Nuance essentielle : ajouter une espèce qui utilise des mécanismes existants est surtout du contenu. Ajouter une région, un type d’effet inconnu, un objectif inédit ou un nouveau gameplay nécessite aussi des branchements de code. Les chapitres suivants indiquent lesquels.

C — Enregistrer une région réellement utilisable

C.1 Déclaration et ordre de progression

Dans le tableau REGIONS de src/config/Regions.js, insérez ce fragment après Hoenn, avant l’entrée Sinnoh encore indisponible. Ne créez pas un second tableau REGIONS et ne dupliquez pas Sinnoh.

Object.freeze({id:'auroria',labelKey:'map_region_auroria',available:true}),

available: true signifie « jouable », pas « déverrouillée pour toutes les parties ». FeatureAccessSystem.getRegionAccessStatus() considère les régions disponibles dans cet ordre : la région précédente doit avoir sa ligue gagnée et toutes ses espèces régionales capturées. Un Pokédex régional vide ne compte pas comme complet. Ici, Auroria suit donc Hoenn.

Changer l’ordre des régions change les prérequis d’entrée. Si vous voulez une région de départ, un embranchement ou une entrée par quête plutôt que par ligue + Pokédex, concevez une autre règle dans le résolveur central et testez-la. Ne contournez pas la règle en cachant un bouton.

C.2 Point d’arrivée

Ajoutez dans REGION_START_LOCATIONS de src/config/ContentAccessRules.js :

auroria: 'auroria_start',

Ce lieu doit exister, porter region: 'auroria' et avoir sa géométrie de carte. Le voyage doit passer par LocationSystem.travelToRegion('auroria'), pas par une affectation depuis l’interface à save.player.region. Cette commande vérifie la politique d’entrée et l’expédition active.

D — Construire les lieux et leur graphe

Le parcours pédagogique est :

Aubeval ↔ Sentier (3 victoires) ↔ Florécité (arène + rival) ↔ Bois (donjon) ↔ Sommet (ligue)

Voici l’objet à fusionner avec LOCATIONS_CONTENT dans locations-content.js. Les exports complets montrés sont des modèles : dans un projet existant, conservez les autres entrées.

export const LOCATIONS_CONTENT = {
  "auroria_start": {
    "region": "auroria",
    "kind": "town",
    "connections": [
      "auroria_path"
    ],
    "winsToClear": 0,
    "badgesRequired": 0,
    "shop": "auroria_store"
  },
  "auroria_path": {
    "region": "auroria",
    "kind": "route",
    "connections": [
      "auroria_start",
      "auroria_city"
    ],
    "winsToClear": 3,
    "badgesRequired": 0
  },
  "auroria_city": {
    "region": "auroria",
    "kind": "town",
    "connections": [
      "auroria_path",
      "auroria_forest"
    ],
    "winsToClear": 0,
    "badgesRequired": 0,
    "champion": "auroria_ivy",
    "shop": "auroria_store"
  },
  "auroria_forest": {
    "region": "auroria",
    "kind": "dungeon",
    "connections": [
      "auroria_city",
      "auroria_summit"
    ],
    "winsToClear": 0,
    "badgesRequired": 1
  },
  "auroria_summit": {
    "region": "auroria",
    "kind": "town",
    "connections": [
      "auroria_forest"
    ],
    "winsToClear": 0,
    "badgesRequired": 1,
    "champion": "auroria_league"
  }
};
  • connections définit les voisins. Ajoutez le lien retour ; une relation à sens unique n’est pas inventée automatiquement.
  • kind accepte town, route, sea, dungeon. Un lieu nommé « forêt » n’est pas automatiquement un donjon : c’est le champ qui le décide.
  • badgesRequired est un nombre de badges d’arène de la région, pas une liste de badges précis.
  • winsToClear est un seuil de victoires sauvages qui permet la propagation de l’accès depuis ce lieu. 0 signifie aucun seuil. Cela n’impose pas de finir le gardien d’un donjon.
  • shop est un id de ShopDB ; champion est un id de TrainerDB ou LeagueDB.
  • group, facultatif, fait partager des objectifs/statistiques à plusieurs sous-zones. Ne donnez pas le même groupe à toute la région : les combats d’une route valideraient alors les autres.
  • weather, facultatif, fixe une météo reconnue dans src/data/battle/BattleFields.js.

Un lieu relié n’est pas nécessairement déverrouillé : badges, portes exceptionnelles et nettoyage des voisins restent évalués par FeatureAccessSystem.

Le kit fournit une carte schématique sans noms incrustés : les noms sont des libellés localisés posés par le jeu. Une nouvelle carte de production doit être votre propre ressource.

Le décor de combat est un autre réglage

Dans src/config/LocationBackgrounds.js, SCENE_BY_LOCATION peut préciser le décor :

auroria_forest: 'forest',
auroria_summit: 'mountain',

Le nom doit être dans BACKGROUND_SCENES, avec sa ressource dans assets/images/bg/. Sans exception, le décor est déduit du type : un donjon prend le décor de grotte par défaut. Ce choix a aussi un effet sur DungeonRules.depthFor() : les scènes de type grotte/montagne ont plusieurs étages, une forêt suit la règle non-grotte. Ne promettez pas un nombre d’étages en vous fondant seulement sur le nom du lieu.

Si vous ajoutez une scène totalement nouvelle, il faut également sa déclaration, sa ressource et le raccordement CSS existant. Déposer un PNG sans l’enregistrer ne crée pas un décor utilisable.

Dans encounters-content.js :

    },
    {
      "species": "pidgey",
      "minLevel": 3,
      "maxLevel": 6,
      "rarity": "uncommon"
    }
  ],
  "auroria_forest": [
    {
      "species": "mossling",
      "minLevel": 8,
      "maxLevel": 12,
      "rarity": "common"
    },
    {
      "species": "pikachu",
      "minLevel": 8,
      "maxLevel": 12,

    }

Les trois raretés sont common, uncommon, rare. Utilisez des espèces existant dans PokemonDB, avec minLevel ≤ maxLevel. Les poids effectifs sont ceux des règles de rencontres, pas des pourcentages déduits des noms.

Une table portant l’id d’un lieu existant remplace toute sa liste. Copiez les anciennes rencontres à conserver. Le bouton d’exploration exige des rencontres ; un donjon sans rencontres ne peut pas être lancé même si son rectangle et son type existent.

Les rencontres ordinaires, rencontres de quête, Pokémon errants et équipes de dresseur sont des contextes différents. Ne mettez pas un boss de scénario dans les rencontres communes si sa capture ou sa récompense doit être unique. Utilisez les quêtes/rencontres dédiées et les systèmes existants.

G — Ajouter un Pokémon, une forme ou une évolution

G.1 Espèce — species-content.js

export const SPECIES_CONTENT = {
  "mossling": {
    "dex": 1001,
    "region": "auroria",
    "types": [
      "grass"
    ],
    "stats": [
      50,
      45,
      55,
      65,
      60,
      45
    ],
    "catchRate": 120,
    "xpYield": 65,
    "talents": [
      "overgrow"
    ],
    "hiddenTalent": null,
    "evolutions": []
  }
};
  • dex est un numéro de tri/Pokédex, pas l’id de l’espèce. Choisissez un numéro non utilisé.
  • stats suit : PV, Attaque, Défense, Attaque spéciale, Défense spéciale, Vitesse.
  • region détermine notamment son appartenance au Pokédex régional.
  • talents doit contenir des ids connus. Le talent caché est séparé du tirage normal.
  • catchRate est conservé comme donnée ; la capture actuelle dépend des règles de ball, pas de ce taux d’espèce. Ne promettez pas un nouveau comportement en changeant seulement ce champ.
  • Les quatre attaques actives ne sont pas définies ici : voir le chapitre H.

Textes : pokemon.mossling en FR et EN. Images :

assets/images/pokemon/mossling.png
assets/images/pokemon/shiny/mossling.png

Le kit utilise Bulbizarre comme placeholder, y compris son shiny. Pour votre création, remplacez les images sans changer l’id stable. Le résolveur des chemins reste AssetPaths.pokemonSprite().

G.2 Évolution

Exemples de valeurs du champ evolutions ; la cible et l’objet doivent déjà exister :

evolutions: [{to:'ivysaur',level:16}]
// Or an item evolution, not both examples at once:
evolutions: [{to:'raichu',item:'thunderstone',minLevel:1}]

Pour une nouvelle cible, créez sa définition complète et ses ressources avant de la référencer. Une évolution ne doit pas cloner un Pokémon déjà possédé dans un autre modèle : utilisez le système d’évolution et sa gestion canonique des UID.

G.3 Forme alternative

Fragment à insérer dans FORMS_CONTENT ; fournissez aussi le sprite suffixé :

mossling_winter: {
  species:'mossling',form:'winter',types:['ice'],
  stats:[50,45,60,65,65,35],kind:'alt'
}

Chemin : assets/images/pokemon/mossling_winter.png et, si fourni, son équivalent shiny. Une forme reste la forme de l’espèce mossling; elle n’ajoute pas automatiquement une seconde espèce au total régional. Les conditions d’acquisition d’une forme doivent correspondre à un mécanisme réellement pris en charge ; un champ inventé n’est pas exécuté.

H — Ajouter une capacité réellement utilisable

H.1 Définition complète — moves-content.js

export const MOVES_CONTENT = {
  "chloroshot": {
    "type": "grass",
    "category": "special",
    "power": 55,
    "accuracy": 100,
    "priority": 0,
    "rarity": 2,
    "cooldown": 1,
    "tags": [],
    "effects": [],
    "learnTypes": [
      "grass"
    ]
  }
};
  • category : physical, special, status.
  • power : puissance ; une capacité de statut a une puissance nulle.
  • accuracy : pourcentage ; neverMiss: true est un comportement distinct, si nécessaire.
  • cooldown : multiplicateur du délai d’attaque, pas un nombre de secondes.
  • rarity participe au classement du pool d’apprentissage.
  • priority, hits, tags, bypassDefenseBoosts et effects sont des options connues du moteur.
  • learnTypes : tableau de types compatibles ; learnTypes: ['all'] signifie tous les types. Une liste vide exclut la capacité du tirage naturel, utile pour des signatures.

Textes requis : move.chloroshot et move_desc.chloroshot, dans les deux langues.

H.2 Le piège du learnset

Le Rework actuel ne lit pas un tableau par espèce du type movesAtLevel. MoveLearnset dérive le pool des types et des learnTypes, trie selon ses règles, puis garde MoveConfig.POOL_SIZE entrées. Le niveau ouvre progressivement ce pool ; les attaques stockées valides du Pokémon passent avant le fallback naturel. Une nouvelle capacité compatible ne devient donc pas forcément sa première attaque.

Pour vérifier ce que votre Pokémon obtient vraiment :

import {MoveLearnset} from './src/data/pokemon/MoveLearnset.js';
console.log(MoveLearnset.poolFor(['grass']));
console.log(MoveLearnset.movesForLevel(['grass'],20));

Le kit propose aussi une CT vendue en boutique. Elle déverrouille la capacité chez une cible compatible via ItemUseSystem ; le joueur choisit ensuite son emplacement actif via MoveLearningSystem et l’interface existante. Ne changez pas directement pokemon.moves depuis un nouveau panneau.

Pour un nouveau système de learnsets par espèce, il faut explicitement faire évoluer le modèle statique, son dépôt/validation, MoveLearnset, l’apprentissage, l’entraînement et les tests. Ajouter un champ inconnu dans la définition d’une espèce ne suffit pas.

H.3 Effets existants et effet inédit

Exemple d’effet reconnu à ajouter dans effects, si vous voulez un risque d’empoisonnement :

{kind:'status',status:'poison',chance:20,secondary:true}

chance: 20 signifie 20 %, pas 0.20. Le vocabulaire est dans MoveEffectKinds.js et les paramètres dans docs/BATTLE_EFFECTS.md. Les effets sont exécutés par les handlers du moteur de combat ; MoveDB.validate() refuse un kind inconnu.

Un effet vraiment inédit nécessite : une constante, un handler dans le pipeline d’effets approprié, son enregistrement, les conditions/paramètres validés, les textes de journal FR/EN et des tests (résistance/immunité, KO, multi-coups et sauvegarde si un état persiste). Ne stockez pas une fonction dans la table et ne rajoutez pas un second moteur de dégâts dans l’UI.

I — Objets, CT, talents et ressources

I.1 Les deux objets du kit — items-content.js

export const ITEMS_CONTENT = {
  "auroria_pass": {
    "kind": "key",
    "price": 0,
    "image": "pokeflute.png"
  },
  "auroria_tm_chloroshot": {
    "kind": "tm",
    "price": 1200,
    "image": null,
    "move": "chloroshot"
  }
};

Le laissez-passer est un key gratuit accordé par quête, pas un objet à vendre. La CT a un prix et référence une vraie capacité. image: null utilise le visuel générique prévu ; l’image de flûte du laissez-passer est un placeholder existant à remplacer.

Familles connues : held, tm, hm, ball, stone, evolution, fossil, key, consumable, candy, treasure, keystone, memory (ItemKinds.js). Les champs ne créent pas automatiquement un usage. ItemUseSystem décide quels objets sont effectivement utilisables et sur quelles cibles.

Exemples de mécanismes déjà branchés : CT/CS (move), évolution déclarée, bonbon niveau, vitamines, fossiles par le laboratoire. Pour un nouvel objet actif, auditez ItemUseRules, ItemUseSystem, la sélection de cible, la consommation, les événements et la sauvegarde unique.

I.2 Poké Balls

Une nouvelle ball nécessite une définition kind: 'ball', son bloc ball et sa ressource SVG. rate est le taux de base ; les conditions reconnues viennent de BallConditions.js et sont évaluées par BallRateRules. Les filtres choisissent la ball lancée. Ne dupliquez pas ce calcul pour une rencontre régionale. Le stock automatique des boutiques reste piloté par ShopRules.

I.3 Talent

Pour réutiliser un effet existant, ajoutez une entrée complète dans TALENTS_CONTENT, puis sa traduction talent.<id>.name / .desc. Exemple de forme reconnue, inspirée d’Engrais :

export const TALENTS_CONTENT = {
  plateau_growth:{
    rarity:1,affinity:['grass'],
    effects:[{kind:'power',mult:1.35,when:{moveTypes:['grass'],selfHpBelow:0.35}}]
  }
};

Les paramètres de condition sont ceux réellement lus par les règles d’effets. Un talent inédit suit le même principe qu’une capacité inédite : vocabulaire, handler, conditions validées, textes, tests. Un texte vantant un bonus ne l’implémente pas.

  1. stockez son UID dans le nouveau modèle ;
  2. demandez les autorisations à PokemonUsageSystem avec une action reconnue ;
  3. utilisez les systèmes de sélection communs du PC / des installations ;

R — Nouveau gameplay : le modèle du Carnet de terrain

R.1 Définir le comportement avant le code

Le Carnet est proposé à Auroria. Après trois victoires sauvages sur une route, hors combat, on peut étudier ce site une seule fois et recevoir 250 Pokédollars. Changer de partie ne doit pas transférer les sites ou les récompenses. Le nombre de sites est dérivé de la liste des ids ; on ne sauvegarde pas deux compteurs qui pourraient diverger.

Ce module est un exemple de gameplay régional, pas une nouvelle installation permanente. Le panneau peut donc se masquer hors d’Auroria. Si vous souhaitez un déverrouillage permanent après une quête, déclarez-le dans FeatureAccessSystem et utilisez ce statut dans le système.

R.2 Modèle complet — src/data/save/FieldJournalData.js

/** @file FieldJournalData.js @brief Stores only surveyed site IDs; counts are derived. */
import { BaseModel } from "../core/BaseModel.js";
export class FieldJournalData extends BaseModel {
  constructor(data = {}) {
    super("FieldJournalData", "Data");
    this.deserialize(data);
  }
  deserialize(data = {}) {
    this.sites = [
      ...new Set(
        (Array.isArray(data?.sites) ? data.sites : []).filter(
          (id) => typeof id === "string" && id.length > 0,
        ),
      ),
    ];
  }
  has(locationId) {
    return this.sites.includes(locationId);
  }
  add(locationId) {
    if (!locationId || this.has(locationId)) return false;
    this.sites.push(locationId);
    return true;
  }
  serialize() {
    return { sites: [...this.sites] };
  }
}

La désérialisation accepte un champ absent et retire les doublons/valeurs invalides. La sérialisation renvoie une copie de la liste. Les méthodes ne connaissent ni un bouton, ni une traduction, ni le DOM. Les ids inconnus mais textuels sont conservés comme faits, pour ne pas perdre un ancien site simplement parce qu’un module de contenu est temporairement absent.

Le modèle seul n’est pas encore sauvegardé : les trois branchements dans SaveData et la migration sont décrits au chapitre U. N’oubliez pas l’un de ces trois points.

S.3 Système complet — src/systems/FieldJournalSystem.js

/** @file FieldJournalSystem.js @brief Sample-only gameplay: one paid survey per cleared route. */
import { BaseSystem } from "./BaseSystem.js";
import { SaveSystem } from "./SaveSystem.js";
import { BattleSystem } from "./BattleSystem.js";
import { FeatureAccessSystem } from "./FeatureAccessSystem.js";
import { LocationSystem } from "./LocationSystem.js";
import { LocationDB } from "../data/world/LocationDB.js";
import { FieldJournalRules as Rules } from "../config/FieldJournalRules.js";
import { EventBus } from "../core/EventBus.js";
import { FieldJournalChangedEvent } from "../core/events/FieldJournalChangedEvent.js";
export class FieldJournalSystem extends BaseSystem {
  static _instance = null;
  static getInstance() {
    return this._instance || (this._instance = new FieldJournalSystem());
  }
  constructor() {
    super("FieldJournalSystem", "System");
  }
  getSnapshot() {
    const save = SaveSystem.getInstance().getCurrentSave();
    const location = LocationDB.getInstance().getById(
      LocationSystem.getInstance().getCurrentLocationId(),
    );
    const visible = !!save && save.player.region === Rules.REGION;
    const wins =
      save && location ? save.statistics.wildWinsInGroup(location.id) : 0;
    const already = !!location && !!save?.fieldJournal.has(location.id);
    const reason = already
      ? "already"
      : BattleSystem.getInstance().isActive()
        ? "battle"
        : location?.kind !== "route"
          ? "location"
          : wins < Rules.MIN_WINS
            ? "wins"
            : "ready";
    return {
      visible,
      locationId: location?.id || null,
      wins,
      required: Rules.MIN_WINS,
      total: save?.fieldJournal.sites.length || 0,
      reward: Rules.REWARD,
      reason,
      canSurvey:
        visible &&
        reason === "ready" &&
        FeatureAccessSystem.getInstance().isLocationUnlocked(location.id),
    };
  }
  survey() {
    const model = this.getSnapshot(),
      save = SaveSystem.getInstance().getCurrentSave();
    if (!save || !model.canSurvey || !save.fieldJournal.add(model.locationId))
      return false;
    save.currencies.add(Rules.CURRENCY, Rules.REWARD);
    SaveSystem.getInstance().saveCurrent();
    EventBus.getInstance().dispatch(
      new FieldJournalChangedEvent(model.locationId),
    );
    return true;
  }
}

Lisez les deux méthodes séparément :

  • getSnapshot() est une requête pure pour l’UI. Elle dérive lieu, victoires, motif, montant et possibilité de commande. Rafraîchir la vue ne rapporte rien et ne sauvegarde rien.
  • survey() relit la vraie possibilité, marque le site, verse la récompense, sauvegarde une fois puis signale le changement. Un second clic ne paie pas et n’écrit pas.

La règle interdit le versement pendant un combat. Les trois victoires d’une chaîne sauvage ne la terminent pas automatiquement : le joueur peut quitter normalement, puis étudier le site. Le bouton ne doit pas conclure le combat ou forger un PokemonDefeatedEvent.

Ce gameplay est une commande instantanée : il n’a pas besoin d’un setInterval ni d’un nouveau moteur de boucle. Si vous ajoutez une production dans le temps, utilisez BaseSystem.update(dt), un état sauvegardé clair et une politique explicite de temps hors ligne ; n’inventez pas un rattrapage qui dupliquerait les récompenses à chaque rechargement.

U — Sauvegarder, migrer et changer de partie sans perte

U.1 Trois branchements indispensables dans SaveData

Importez FieldJournalData, puis ajoutez les lignes aux endroits correspondants :

import {FieldJournalData} from './FieldJournalData.js';

// In the constructor:
this.fieldJournal=new FieldJournalData();

// In the object returned by serialize():
fieldJournal:this.fieldJournal.serialize(),

// In deserialize(data):
this.fieldJournal=new FieldJournalData(data.fieldJournal);

Ce sont des fragments à placer dans la classe, pas un fichier exécutable isolé. Le premier prépare une partie neuve, le deuxième écrit le fait, le troisième le relit. Une seule ligne manquante donne un bug qui paraît aléatoire après rechargement.

U.2 Migration pure 20 → 21 de l’exemple

Fichier src/data/save/migrations/MigrationV20ToV21.js :

/** @file MigrationV20ToV21.js @brief Sample-only next schema; existing fields remain unchanged. */
import { FieldJournalData } from "../FieldJournalData.js";
export const MigrationV20ToV21 = Object.freeze({
  from: 20,
  to: 21,
  migrate(raw) {
    return {
      ...raw,
      version: 21,
      fieldJournal: new FieldJournalData(raw.fieldJournal).serialize(),
    };
  },
});

Puis :

  1. importez cette migration dans SaveMigrator.js et ajoutez-la à la fin de la chaîne ;
  2. passez SaveSchema.VERSION de 20 à 21 dans la copie de démonstration ;
  3. synchronisez GameConfig.VERSION, package.json, les deux versions racine de package-lock.json ;
  4. mettez à jour le contrat de schéma dans les tests et documentez la nouvelle donnée ;
  5. testez l’absence du champ, son contenu valide/invalide, le JSON round-trip et l’absence de mutation des autres modèles.

L’exemple ne touche pas aux UID, à la Pension, aux FIFO, aux batailles d’Entraînement ou à l’horloge de Mine. Une migration ne doit pas remettre ces états à zéro pour faciliter son nouvel ajout. Le migrateur traite les anciens formats avant les modèles ; ne mettez pas de logique d’import historique dans un panneau.

U.3 Ce qu’on sauvegarde et ce qu’on ne sauvegarde pas

À conserver À dériver / laisser transitoire
ids de sites étudiés nombre de sites
propriété et activation d’un module DOM du switch
mode de pilote choisi chemin calculé à chaque étape
DTO de combat qui doit reprendre exactement faux adversaire recréé depuis son espèce
vraie échéance d’une action persistante compteur UI recalculé
UID d’un Pokémon affecté copie du Pokémon dans chaque activité

Un délai de relance en cours est volontairement transitoire et annulé au changement de partie/lieu. Ce n’est pas la même politique que le délai manuel persistant du sondage de Mine. Ne les généralisez pas sans décider le comportement attendu.
